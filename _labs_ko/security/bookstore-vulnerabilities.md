## 문제

오래된 서비스는 오래된 라이브러리를 끌어오고, 오래된 라이브러리는 알려진 CVE를 품습니다. 내가 선언한 것만이 아니라 그 아래 전이(transitive) 의존성까지요. 실제로 어떤 의존성이 취약한지, 어느 버전이 고치는지, 그 수정이 다른 걸 깨지 않는지 따지는 건 careful하고 티 안 나는 일입니다.

Bob의 프리미엄 Java Vulnerabilities 패키지는 해석된 의존성 트리를 스캔하고, 고칠 수 있는 걸 끌어올리고, 중요하게도 **고친 뒤 다시 스캔해서 확인**합니다. 이 랩은 그걸 일부러 취약하게 만든 앱에 돌립니다. 여기서 가르치는 함정은 절차적입니다. 이 워크플로는 단독으로 돌릴 때와 업그레이드 뒤에 체인으로 돌 때 동작이 크게 다릅니다. 참고: 이건 **유료 프리미엄 패키지**라, 활성화된 계정에서만 실행됩니다.

## 프롬프트

### Step 1 - Java 21 과 Maven 설치

`java -version` 이 21 이상이고 `mvn -v` 가 되면 건너뛰세요. **Windows** - <https://developer.ibm.com/languages/java/semeru-runtimes/downloads/> 에서 Semeru 21 `.msi`(Set JAVA_HOME + Add to PATH), Maven 은 <https://maven.apache.org/download.cgi>. **macOS** - `brew install --cask semeru-jdk-open@21 && brew install maven`.

### Step 2 - 애플리케이션 받기

**[bob-lab-bookstore.zip](https://github.com/ce-aie-labs/bob-labs/releases/download/lab-assets/bob-lab-bookstore.zip)** 을 받아 압축을 풉니다. `START-HERE.md` 가 있는 폴더에서 터미널을 여세요. 안에 든 **Legacy Bookstore** 는 일부러 오래되고 취약한 라이브러리를 고정합니다. 예를 들어 **H2 1.4.200**(CVE-2022-23221), **log4j 1.2.17**(CVE-2019-17571).

### Step 3 - Vulnerabilities 워크플로를 단독으로 실행

Bob에서 `app` 폴더를 엽니다. 워크플로를 시작해 **Vulnerabilities** 플로우를 고릅니다. **단독으로** 돌리세요. 다른 워크플로 뒤에 체인으로 붙지 않게 하세요(중요, 팁 참고).

```
이 프로젝트에 취약점 조치 워크플로를 단독으로 돌려주세요.

해석된 의존성 트리(전이 포함)를 스캔하고, 취약한 의존성을 패치가 있는 가장 작은
버전 변경으로 고치고, 애플리케이션 동작은 바꾸지 말고, 다시 스캔해서 남은 걸 확인해 주세요.
```

### Step 4 - 독립 스캐너로 검증

요약을 그대로 믿지 마세요. Bob이 아닌 스캐너를 같은 트리에 돌려 보세요. 예: [`osv-scanner`](https://github.com/google/osv-scanner).

```
osv-scanner --lockfile pom.xml    # 또는 빌드 산출물을 스캔
```

그 결과를 Bob이 고쳤다고 한 것, 남았다고 한 것과 대조합니다.

## 기대 결과

- [ ] 선언된 의존성만이 아니라 **전이 트리**까지 스캔함 - 실제 기록에서 **직접 10개 → 전이 37개** 스캔으로 **43개 CVE** 를 드러냈고, 독립 `osv-scanner`(41개)와 약 5% 이내
- [ ] 취약점을 **작고 정확한 변경**으로 끌어올림 - 실제 단독 실행에서 `pom.xml` 두 줄 변경으로 **23 → 0**, 애플리케이션 동작은 안 바꿈
- [ ] 막 올리는 게 아니라 **수정 버전을 근거로** 고름 - 어떤 라인이 현재 메이저(예: Spring 6.1.x)에 패치가 없다는 걸 짚고 패치가 있는 마이너(6.2.x)를 선택
- [ ] **고친 뒤 다시 스캔해서 스스로 확인**: 해결 N, 남음 0, 신규 유입 0. 그리고 Step 4의 독립 스캔도 일치
- [ ] 어떤 패키지가 왜 움직였는지 - 줄어든 숫자가 아니라 리뷰에 들고 갈 만큼 읽히게

이 픽스처와 그 현대화 형태에 프리미엄 워크플로를 실제로 돌린 기록(43개 CVE 탐지, 단독 23 → 0, 재스캔 자기확인, IBM client-engineering Bob-for-Java 평가)에서 시드했습니다. 정확한 개수는 시작 상태에 따라 달라집니다.

## 팁

- 이건 프리미엄 패키지라 Java Vulnerabilities가 활성화된 계정에서만 실행됩니다. 데모 전에 접근 권한을 확인하세요.
- **단독으로 돌리세요.** 여기서 제일 중요한 것: 취약점 수정은 Flow Selection 화면에 **자기 항목으로 안 뜹니다.** 그래서 Java Upgrade 뒤에 자동 체인으로 붙기 쉽습니다. 체인으로 돌린 실제 기록은 오히려 41 → 23이지만 **신규 10건 유입**에 **재스캔 없음** 이었습니다. 워크플로는 하나씩 돌리고, 사이에 재스캔하세요.
- **헤드라인 숫자 말고 어떤 패키지가 움직였는지 읽으세요.** 리뷰하는 사람에게는 "23개 줄었다" 보다 "hsqldb가 X에서 Y로" 가 중요합니다.
- 재스캔이 게이트입니다. 고친 뒤 재스캔을 안 했다면 그건 결과가 아니라 주장입니다. 직접 스캔하세요(Step 4).

## 응용

1. **보안 먼저, 업그레이드 나중**: 노출이 급하면 Java나 프레임워크 버전은 그대로 두고 취약점만 고치고, 버전 업은 따로 잡으세요.
2. **탐지기 벤치마크**: `osv-scanner` 를 먼저 돌리고 그다음 워크플로를 돌려, 이 트리에서 둘이 얼마나 가까운지 보세요. 믿을 수 있는 탐지가 핵심입니다.
3. **우리 프로젝트로**: 우리 서비스에 단독으로 돌리고 재스캔하세요. 사이에 스캔 없이 다른 워크플로에 절대 체인하지 마세요.
