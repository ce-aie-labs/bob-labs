## 문제

모듈에 테스트가 없거나, 있어도 해피패스만 커버한다. 제대로 된 스위트를 손으로 작성하는 일 - 픽스처, 엣지 케이스, 귀찮은 에러 경로 - 은 계속 뒤로 밀리는 딱 그런 지루한 작업이다.

## 프롬프트

**Agent 모드**에서 실행:

```
@/<모듈/경로>에 대한 테스트 스위트를 이 프로젝트의 기존 테스트
프레임워크와 컨벤션으로 작성해줘.

해피패스, 엣지 케이스(빈 입력, 경계값, 잘못된 값), 그리고 에러 경로까지
커버해줘 - 뻔한 케이스만이 아니라. 각 테스트의 단언문은 함수가 그냥
도는지가 아니라 실제 동작을 확인하게 만들어줘.

그다음 테스트를 실행하고, 테스트 자체가 틀려서 실패하는 건 고쳐줘.
```

## 기대 결과

- [ ] 프로젝트의 실제 프레임워크와 스타일로 작성된 테스트 - 기존 픽스처와 헬퍼를 재사용하고 현재 테스트 구조에 맞춤 - 낯선 프레임워크를 갖다 붙인 게 아니라
- [ ] 해피패스를 넘어선 커버리지: 빈 입력, 경계값, 잘못된 값이 각각 케이스가 되고, 에러/예외 경로까지 - 같은 성공 호출의 변형 네 개가 아니라
- [ ] 실제 동작과 구체적인 기대값을 확인하는 단언문 - "뭔가 반환됐다"나 "예외가 안 났다"가 아니라
- [ ] Bob이 스위트를 실행하고 테스트가 통과함 - 또는 대상 코드에서 발견한 진짜 버그를 설명함. 초록불 만들려고 단언문을 약화시키는 게 아니라

테스트 스캐폴딩 자동화는 IBM Bob [Level 3 코스](https://ibm.github.io/bob-l3/)가 Bob이 잘하는 세 가지 중 하나로 꼽는 일입니다. Tailor 모듈에서 생성된 `AGENTS.md`도 데모 레포의 실제 테스트 함정 - 오래된 모델을 쓰는 백엔드 테스트, 테스트가 아예 없는 프론트엔드 - 을 짚었는데, 좋은 테스트 프롬프트라면 존중해야 할 맥락입니다.

## 팁

- 기존 테스트도 짚어줄 것("`@/tests`의 스타일에 맞춰"). 그래야 셋업을 새로 지어내지 않고 픽스처와 프레임워크를 재사용한다.
- 통과시키려고 테스트를 약화시키는 실패 모드를 주의할 것. 단언문을 느슨하게 해서 초록불을 만들면 거짓 통과다 - 원래 단언문이 왜 실패했는지 먼저 설명하라고 할 것.
- 엣지 케이스를 명시적으로 요구할 것. "테스트 작성해줘"만으로는 해피패스 커버리지가 나오는 경향이 있다. 빈 값/경계값/잘못된 값을 짚어야 쓸모있는 케이스가 강제된다.
- 아직 테스트 셋업이 없으면 Bob에게 하네스부터 스캐폴딩시키고("이 스택에서 보통 하는 방식으로 테스트 프레임워크를 셋업해줘"), 두 번째 패스에서 테스트를 생성할 것.

## 응용

1. **레거시 코드 특성화**: "`@/<모듈>`의 *현재* 동작을 있는 그대로 포착하는 테스트를 작성해줘. 안전하게 리팩토링하게 - 이상적인 게 아니라 특성화 테스트로."
2. **커버리지 공백 메우기**: "`@/<모듈>`에서 기존 테스트가 커버 안 하는 분기가 뭐야? 그 케이스들만 추가해줘."
3. **버그 하나 재현**: "`<버그>`를 재현하는 실패 테스트를 작성하고, 통과할 때까지 코드를 고쳐줘."
