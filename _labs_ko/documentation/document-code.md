## 문제

파일의 공개 함수에 docstring이 없거나, README가 코드의 실제 동작과 어긋나 있다. 손으로 문서화하는 건 보상이 적은 잡일이라 늘 목록 맨 위까지 올라오지 못한다.

## 프롬프트

**Agent 모드**에서 실행:

```
@/<파일/경로>의 모든 공개 함수에 간결한 docstring을 추가해줘 - 뭘 하는지,
파라미터가 뭔지, 뭘 반환하거나 예외를 던지는지 한두 문장으로. 이 레포에서
이미 쓰는 docstring 스타일에 맞추고, 동작이나 로직은 바꾸지 마.

사소한 비공개 헬퍼는 건너뛰고, 코드를 그대로 옮겨 적는 잡음 주석은
넣지 마.
```

## 기대 결과

- [ ] 각 공개 함수에 docstring - 뭘 하는지, 파라미터, 반환/예외 동작 - 레포의 기존 스타일(JSDoc, Python docstring, 이미 쓰는 무엇이든)로. 낯선 컨벤션이 아니라
- [ ] 동작 변경 없음: diff가 주석과 docstring뿐이라 로직 전체 재리뷰 없이 안전하게 머지 가능
- [ ] 잡음은 건너뜀 - 뻔한 코드를 옮겨 적는 `// i 증가` 같은 주석 없음, 사소한 비공개 헬퍼는 그대로 둠
- [ ] 함수 목적이 코드만으로 정말 불분명한 곳은, Bob이 자신 있게 틀린 설명을 지어내는 대신 표시하거나 물어봄

"문서화, 커밋 메시지, 테스트 스캐폴딩 등 개발의 잡일 자동화"는 IBM Bob [Level 3 코스](https://ibm.github.io/bob-l3/)가 꼽는 세 가지 핵심 강점 중 하나입니다. Tailor 모듈은 바로 이걸 규칙으로 인코딩하고("모든 공개 함수에 간결한 docstring"), Bob Shell 모듈은 Bob에게 "readme를 확인하고 개선할 수 있는지 봐줘"라고 요청하며 시작합니다.

## 팁

- 문서 전용으로 명시적으로 제한할 것("동작은 바꾸지 마"). 열린 문서화 프롬프트는 Bob이 코드까지 "개선"하게 유도해, 안전한 주석 전용 diff를 진짜 리뷰로 바꿔버린다.
- 기존 스타일에 맞추지 않으면 불일치가 생긴다. 레포가 JSDoc을 쓰면 그렇게 말하고, 파일 절반이 이미 문서화돼 있으면 그걸 따르라고 할 것.
- 가장 좋은 docstring은 *무엇*이 아니라 *왜*를 말한다. Bob 출력이 함수 이름을 문장으로 다시 쓴 수준이면, 의도와 함정을 설명하라고 할 것.
- 규칙과 엮을 것(Bob Rules 랩 참고). 그래야 사후에 모든 파일에 이걸 돌리는 대신 새 코드가 자동으로 문서화된다.

## 응용

1. **README 갱신**: "`@/<모듈>`을 읽고 사용 예시와 명령어가 지금 코드의 실제 동작과 맞도록 `README.md`를 업데이트해줘."
2. **까다로운 함수 설명**: "`<함수>`에 시그니처만이 아니라 비자명한 알고리즘과 왜 이렇게 짰는지 설명하는 docstring을 추가해줘."
3. **모듈 개요 생성**: "`@/<폴더>` 패키지용 짧은 `README.md`를 써줘: 무슨 용도인지, 주요 진입점, 조각들이 어떻게 맞물리는지."
