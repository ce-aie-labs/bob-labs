## 문제

Java 8을 21로 올리는 건 작업 하나가 아닙니다. 의존성을 훑고, 모든 파일에 걸쳐 패키지 이름을 바꾸고, 컴파일이 되기도 전에 빌드 플러그인부터 교체하고, 취약한 라이브러리를 끌어올리고, 그다음 깨진 걸 며칠이고 고치는 일입니다. 뭘 해야 하는지는 다들 압니다. 그걸 순서대로 일주일 동안 하는 게 아무도 자원하지 않는 부분이죠.

Bob의 Java Modernization 패키지는 그 단계들을 **정해진 워크플로**로 돌립니다. 의존성을 알아서 파악하고, 기계적인 변환은 OpenRewrite 레시피로 처리하고, 알려진 취약점을 조회해서 고치는 걸 **자기 단계 중 하나로** 수행하고, 빌드가 통과할 때까지 고치고 다시 빌드합니다. 이 랩은 그 워크플로를 실제 애플리케이션에 돌리고, 결과를 돌아가는 앱에 대고 확인합니다.

**유료 프리미엄 패키지입니다.** Java Modernization 이 켜져 있는 계정에서만 워크플로가 시작됩니다. 시작 전에 확인하세요. 없으면 Step 2에서 아무 일도 일어나지 않습니다.

## 프롬프트

### Step 1 - 조사가 끝난 상태에서 시작

[레거시 자바 애플리케이션 현황 파악하기](../petclinic-assess/)에서 압축을 푼 `bob-lab-petclinic` 폴더가 필요합니다. Java 21이 깔려 있고 `java check.java` 가 `0 / 3` 을 찍는 상태요. 그 랩은 20분이면 되고, 거기서 받은 계획이 이번 실행 결과와 대조할 기준이 됩니다.

Bob에서 `app` 폴더를 엽니다.

### Step 2 - 워크플로 시작

**Start Workflow** 버튼을 쓰거나, `/start-java-mod` 스킬을 쓰거나, Agent 모드에서 이렇게 시킵니다.

```
이 프로젝트에 Java Upgrade 워크플로를 돌려주세요.

목표: Java 21, Spring Boot 3.x
빌드 도구: Maven
배포판: Semeru

기존 테스트를 약화시키지 마세요. 컴파일을 위해 import 나 API 호출 형태를 바꾸는 건
괜찮습니다. 하지만 테스트를 지우거나, 비활성화하거나, 검증을 빼지 마세요. 테스트가
실패하면 테스트가 아니라 코드를 고쳐 주세요.

REST 계약도 바꾸지 마세요. 경로, 요청·응답의 필드 이름과 형식, HTTP 상태코드,
에러 메시지 문자열 전부요.
```

### Step 3 - 물어보면 답합니다

워크플로는 중간에 멈추고 물어봅니다. 이 부분을 놓치는 분이 많으니 잘 보세요. 무엇을 찾았는지 보고하면서 목표 버전을 제안하는데, **그 제안이 항상 원하는 값은 아닙니다.** 실제 실행 기록을 보면 Spring Boot 2.7에서 멈추자고 제안한 경우가 있었습니다. 2.7이 `javax` 를 쓰는 마지막 버전이라 나름 근거 있는 선택이지만, Boot 3을 요청했다면 틀린 답이죠.

그럴 때는 어디로 갈 건지 직접 말해주면 됩니다.

```
2.7 말고 Spring Boot 3.x 로 가주세요. 중간 단계가 필요하면 2.7 을 거쳐도 됩니다.
```

질문에 답하고 계속 돌리세요. 실행 한 번에 네다섯 번쯤 물어보고, 벽시계로 40분 정도 걸립니다. 앉아서 지켜볼 필요는 없지만 한 시간씩 자리를 비우지도 마세요.

### Step 4 - 알아서 하는 걸 지켜봅니다

도는 동안 diff 말고 **작업 목록의 단계 이름**을 보세요. 기록된 실행들은 `Fix errors preventing project build` → **`Fix Vulnerabilities`** → `Validate Fixes` 같은 단계를 지나갑니다. 취약점 단계는 아무도 시키지 않았습니다. 워크플로에 들어 있는 겁니다.

지나가면서 눈여겨볼 게 세 가지 있습니다.

- 이 프로젝트가 뭘 쓰는지 **묻지 않고** 의존성 트리와 자바 환경을 직접 읽습니다
- 기계적인 변환은 **OpenRewrite 레시피**로 처리합니다. `javax` → `jakarta` 이름 변경이나 없어진 API 교체는 모델이 파일마다 추측하는 게 아니라 레시피 한 번 실행입니다
- 착지한 버전에 대해 **알려진 취약점을 조회해서** 끌어올립니다. 덤으로 해주는 게 아니라 자기 단계로요

### Step 5 - 결과를 확인합니다

끝나면 압축 푼 폴더로 돌아와서:

```
java check.java
```

Bob의 요약을 읽는 게 아닙니다. 직접 빌드하고, 클래스 파일을 읽고, 테스트를 돌리고, 패키징된 앱을 띄워서 실제 요청에 응답하는지 물어봅니다.

### Step 6 - `demo.html` 을 다시 엽니다

첫 랩에서 쓴 그 파일입니다. 밑바닥 런타임은 통째로 바뀌었는데 화면은 똑같아야 합니다. 수의사 6명, 주인 10명 그대로요.

### Step 7 - 남은 건 다시 맡깁니다

세 줄 중에 초록이 아닌 게 있으면, 그 이유가 적힌 파일을 워크플로에 주고 계속 돌리세요. 고치고 빌드하고 다시 고치는 그 반복이 이 패키지의 핵심이고, 거기서 멈추는 게 실행 하나를 통째로 버리는 가장 흔한 방법입니다.

```
아직 빌드가 안 끝났습니다. 출력을 붙일 테니 원인을 찾아서 고치고, 다시 빌드해서
통과할 때까지 반복해 주세요. 테스트는 약화시키지 마세요.
```

빌드가 실패했으면 `build.log`, 빌드는 되는데 안 뜨면 `boot.log` 를 같이 주세요.

## 기대 결과

- [ ] 긴 편집 한 덩어리가 아니라 **이름이 붙은 단계들로 도는 워크플로** - 빌드, 수정, 취약점, 검증을 지나가는 작업 목록이 보이고, `Fix Vulnerabilities` 가 시키지 않았는데 나타남
- [ ] **OpenRewrite 레시피가 실제로 적용됨** - 어떤 레시피를 돌렸는지 Bob이 말하고, `javax` → `jakarta` 변환이 파일 하나씩이 아니라 한 번에 코드베이스 전체에 반영됨
- [ ] **취약점 조회 결과가 나옴** - 어떤 패키지를 찾았고, 어느 버전으로 올렸고, 못 올린 건 무엇인지
- [ ] `java check.java` 가 주장이 아니라 사실로 확인해 줌:

```
  [ OK ]  빌드        BUILD SUCCESS
  [ OK ]  테스트      169개 통과 · 비활성 0 · 검증문 225
  [ OK ]  기동        HTTP 200  /petclinic/api/vets

  바뀐 것
     Java 바이트코드           8  →  21
     Spring Boot               2.1.5.RELEASE  →  3.5.3
     라이브러리                87개 중 52개 버전 변경
     알려진 취약점 190건       190건이 붙어 있던 버전이 교체됨 · 0건은 그대로

  완료 확인   3 / 3
```

- [ ] **테스트 169개가 그대로 실행되고 통과** - 비활성화된 것도, 빠진 검증문도 없음. 개수가 움직이면 `check.java` 가 테스트 줄을 실패로 찍으니, 이 줄이 초록이면 판정 기준이 안 내려간 것입니다
- [ ] `demo.html` 에 업그레이드 전과 같은 수의사와 주인이 뜸

## 팁

- 프리미엄 패키지가 켜져 있는지 세션 중이 아니라 **시작 전에** 확인하세요. 없으면 Step 2의 프롬프트가 그냥 일반 편집으로 떨어지고 이 랩의 의미가 사라집니다.
- Step 3이 이 랩의 핵심입니다. 일은 워크플로가 하지만 어디에 착지할지는 사람이 정합니다. 내가 안 고른 목표로 가는 게 "그럴듯한데 틀린" 결과에 도착하는 가장 쉬운 길입니다.
- 같은 조건에서 돌려도 기록된 실행들이 전부 같은 곳에 착지하지는 않았습니다. 첫 결과는 납품물이 아니라 확인해야 할 초안으로 다루세요. Step 5가 그것 때문에 있습니다.
- 테스트가 초록이라고 업그레이드가 끝난 게 아닙니다. 테스트는 빌드 안에서 돌고, 앱이 뜨는 건 별개의 사실이며, 이 둘은 생각보다 자주 어긋납니다.
- 취약점은 건수보다 **출력을 읽으세요**. 이걸 리뷰하는 사람에게는 몇 건이 사라졌는지보다 어떤 패키지가 움직였는지가 중요합니다.
- 랩 마지막에 브랜치를 머지하지 마세요. 워크플로는 컴파일되고 테스트를 통과하고 실제로 뜨는 결과까지 가져다줍니다. 동작에 대한 사람의 승인을 대신하지는 않습니다.

## 응용

1. **Liberty 리플랫폼**: `이 프로젝트에 Liberty Replatforming 워크플로를 돌려주세요.` WebSphere 애플리케이션을 Open Liberty로 옮기고, `server.xml` 을 생성·검증하고, `liberty-maven-plugin` 으로 배포합니다.
2. **단위 테스트 생성**: `Unit Test Generation 워크플로를 돌려주세요.` 전략을 먼저 세우고, 생성-실행-수정을 반복해 JaCoCo 커버리지 기준까지 올립니다. 믿고 기댈 테스트가 아직 없는 레거시라면 **업그레이드하기 전에** 돌려볼 만합니다.
3. **보안 먼저, 업그레이드는 나중에**: `Java 와 Spring Boot 버전은 그대로 두고, 이 프로젝트 의존성의 알려진 취약점만 고쳐주세요.` 노출이 급하고 버전 업은 다음 분기 일인 경우가 있습니다.
4. **우리 서비스로**: 같은 워크플로를 우리 저장소에 돌립니다. 위 프롬프트에서 목표 버전만 바꾸면 되고, 테스트와 REST 계약에 대한 두 가지 규칙은 그대로 두세요. 결과를 리뷰할 수 있게 만드는 게 그 두 줄입니다.
